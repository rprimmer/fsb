\section{Verification}
\label{sec:verification}

The strategy follows the principles: the parts that decide what is served get the heaviest
testing, and the tests that matter most let the operating system decide the facts.

\subsection{Continuous integration}

On every change: formatting, vetting, the Go tests under the race detector, the front-end
tests, type checking, a build whose output must equal the committed one, an audit of the
packages that ship, the Chrome browser tests, and timed fuzzing of the four fuzz targets.
A scan for known vulnerabilities in the Go modules runs as well.  The Go tests run on macOS
and Linux; the rest on Linux.  The workflow runs on GitHub's hosted runners for every push
(the repository was private until the 1.0 release and is public since).  Its first run
(2026-10-02) found finding~28 of Section~\ref{sec:history}.  Of the runs since, three
failed, all in the front-end job: an automated TypeScript major-version upgrade that
\code{npm ci} could not install (2026-10-02, never merged); a documentation change whose
run failed the audit of the packages that ship, and which was reverted a minute later, the
revert's run passing (2026-10-02); and the run that first type-checked the unit tests,
whose audit caught a newly published advisory in \code{source-map-js}
(GHSA-68fv-2mgg-jv7q), fixed by the next change (2026-10-06).  The distribution tests of
the table above are not part of it; they run locally, before a release.

\subsection{What testing does not establish}

None of this is a guarantee.  It is a record of what was checked.  A fuzzer reaches only what
its fixture contains, and an early version missed a bug for that reason; the differential test
exists because reasoning about names had been wrong.  Findings~17 through~20
(Section~\ref{sec:history}) were caught by none of the automated layers: no fixture
anywhere contained a UNIX domain socket or a real File Provider placeholder folder, so
nothing had ever exercised the errno either produces, and the Details-panel race needed a
preview that fails, which no test happened to select.  All four were found by using the
running application, not by any automated layer, which is itself a reason to keep doing
that rather than treating the test suite as the last word; Finding~21 was found while
fixing them, by reading the surrounding code rather than by any test.  Independent
reviews were done by an assistant (Section~\ref{sec:untested}) in two sequences: in
September, of Quick Look, background mode and process control; and in October, of the whole
code, as an external review, then of its fixes (which found two further hard-link
bypasses), then of those fixes (which found seven defects, several in the fixes
themselves), and finally of that round, which found nothing new
(Section~\ref{sec:history}); and, after the Linux work of 1.0.2 to 1.0.5, of that work
(eleven findings, two medium, each reproduced; findings 37 and 38).  A professional penetration test was not done.

The Linux distribution tests share one kernel, that of the Docker virtual machine, so
they establish behavior across distributions' user space (C library, tools, file
layout), not across kernels or file systems other than overlay and tmpfs; no Linux
desktop was used.  They also showed how a test can pass without running: the extended
attribute test skips where attributes are unsupported, and in the containers it had
always skipped until \code{/tmp} was moved to tmpfs.
